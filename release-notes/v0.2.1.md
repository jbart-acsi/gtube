This release fixes a first run on Windows that filled the screen with console windows and played nothing. Started from Explorer, gtube gave each program it runs ([yt-dlp](https://github.com/yt-dlp/yt-dlp), Deno, tar and curl) a console window of its own, which Windows Terminal kept open when the program failed. When yt-dlp failed for every track, the player skipped to the next track without limit, so the windows kept coming, and the status line never said why. Ending gtube in Task Manager left those programs running.

## Fixes

- On Windows, the programs gtube runs have no console window and end when gtube ends, however it exits.
- After 3 tracks in a row fail to play, the player stops and the status line shows yt-dlp's last error. When yt-dlp cannot start at all, as when an antivirus has removed it, the message says so.

Checked on Windows 11 with Windows Terminal as the default terminal, gtube started through an Explorer shortcut: from an empty data folder it set itself up and played a radio with no console window, where v0.2.0 opened 3; a curl.exe streaming a track when gtube was killed was gone 2 s later; with a yt-dlp that always fails, playback stopped after 3 tracks. An earlier check, listed below under 77c0367, started gtube from a hidden PowerShell, where even v0.2.0 shows no windows, so it did not test this.

gtube now builds with [Zig](https://ziglang.org) 0.17.0 and gesso 3bb9fea.

## Verifying a download

Each archive is attested by the shared release workflow in wakamex/release-actions. With the [GitHub CLI](https://cli.github.com/):

```sh
gh attestation verify gtube-v0.2.1-x86_64-windows.zip --repo wakamex/gtube \
  --signer-workflow wakamex/release-actions/.github/workflows/binary-release.yml
gh release verify-asset v0.2.1 gtube-v0.2.1-x86_64-windows.zip --repo wakamex/gtube
```
